## Brute-force protection

The following options configure how fast Kirby's (link: docs/guide/security#use-good-passwords text: login brute-force protection) gets activated and how long it takes until the triggered protection is disabled again.

### Number of trials

You can set the number of wrong trials and login challenges (e.g. password reset, two-factor auth) per timeout period (see below) before login gets blocked for the current IP address and user. The default setting is 10.

```php
return [
  'auth' => [
    'trials' => 10
  ]
];
```

### Timeout

You can also set the timeout in seconds for the period of time against which the number of trials is counted. The default is 3600 (one hour). After the timeout is over, login for the current IP address and user is possible again.

```php
return [
  'auth' => [
    'timeout' => 3600
  ]
];
```

## Login methods

The `auth.methods` option controls the available login methods for the Panel and the API.

The available options are:

| Name | Explanation |
| ---- | ----------- |
| `password` | Login with email and password (default) |
| `code` | Passwordless login with just the email address and a code |
| `password-reset` | Password reset via a code |
| `webauthn` | Login with a passkey |

You can read more about the options in the (link: docs/guide/authentication/login-methods#available-login-methods text: guide). The options can be combined like in the following examples. The login view opens with the first method in the list and offers the others as alternatives.

<info>
The `code` and `password-reset` methods and second factors via email need a working email transport configuration. Otherwise verification emails cannot be sent. Find out more about **(link: /docs/reference/system/options/email#email-transport text: how to configure your email transport)**.
</info>

### Login via code

If you want to prevent login via password completely, you can set the login methods option to `code`. The default login via password will be disabled.

```php "/site/config/config.php"
<?php

return [
    'auth' => [
        'methods' => 'code'
    ]
];
```

(image: login.png)

### Login via code & login via password

You can also combine login via code and login via password. The `code` and `password-reset` methods can't be enabled together.

**The first method in the array will be the default login method.**

```php "/site/config/config.php"
<?php

return [
    'auth' => [
        'methods' => ['code', 'password']
    ]
];
```

(image: email-and-password.png)

### Password reset

To enable the password reset form, you can combine the default `password` login method with the `password-reset` method:

```php "/site/config/config.php"
<?php

return [
    'auth' => [
        'methods' => ['password', 'password-reset']
    ]
];
```

(image: password-reset.png)

### Passkeys

To let users log in with a (link: docs/guide/authentication/2fa text: passkey), add the `webauthn` method. Put it first to make passkeys the default:

```php "/site/config/config.php"
<?php

return [
    'auth' => [
        'methods' => ['webauthn', 'password']
    ]
];
```

Keep `password` or `code` enabled next to `webauthn`: users have to be logged in to register their first passkey.

### Two-factor authentication

Users who have set up a (link: docs/guide/authentication/2fa text: second factor) are asked for it after their password. To require a second factor from every user, set the `2fa` option of the `password` method. Users who haven't set up a passkey or authenticator app then get a code via email.

```php "/site/config/config.php"
<?php

return [
    'auth' => [
        'methods' => [
            'password' => ['2fa' => true]
        ]
    ]
];
```

With `'2fa' => true`, the `code` and `password-reset` methods can't be enabled, because they would let users skip the second factor.

(image: 2fa.png)

## Authentication challenges

Whenever a login needs a code or a second factor, Kirby creates an authentication challenge. Kirby comes with three challenges: `webauthn` (passkeys), `totp` (authenticator app) and `email` (code via email). Additional challenges can be added by (link: docs/reference/plugins/extensions/auth-challenges text: auth challenge plugins).

The challenges can be configured with the following options:

### Code timeout

The timeout controls how long a generated login code is valid. The default is 10 minutes.

```php
<?php

return [
    'auth' => [
        'methods'   => ['code', 'password'],
        'challenge' => [
            'timeout' => 5 * 60 // 5 minutes
        ]
    ]
];
```

### Email options

You can customize the sender and the subject of the code emails:

```php
<?php

return [
    'auth' => [
        'methods'   => ['code', 'password'],
        'challenge' => [
            'timeout' => 5 * 60, // 5 minutes
            'email' => [
                'from'     => 'mail@example.com',
                'fromName' => 'My example project',
                'subject'  => 'Login code'
            ]
        ]
    ]
];
```

<info>
If you want to customize the emails even more, take a look how to (link: docs/guide/authentication/login-methods#customize-email-text text: customize the email templates) in the guide. Note also that this configuration is also used for the password-reset emails.
</info>

### Enabled challenges

By default, all three core challenges are enabled. The `challenges` option sets which challenges are enabled and in which order Kirby tries them:

```php
<?php

return [
    'auth' => [
        'challenges' => ['totp', 'email']
    ]
];
```

To turn off a challenge, leave it out of the list.

A challenge is skipped if it isn't available for the user who tries to log in. As a second factor, each challenge needs to be set up by the user first, including codes via email. For login codes, password resets and when every user must use a second factor, the `email` challenge is always available.

If none of the enabled challenges is available, the login stays pending without telling the user, so that attackers can't find out whether a user exists. With `auth.debug` set to `true`, you get the actual error instead.

## Password policy

By default, passwords must be at least 8 characters long. With the `passwords` option, you define your own policy. It applies to all passwords that are set in the Panel or with `$user->changePassword()`.

```php "/site/config/config.php"
<?php

return [
    'auth' => [
        'passwords' => [
            'minlength' => 12,
            'uppercase' => true,
            'lowercase' => true,
            'digits'    => 2,
            'symbols'   => true
        ]
    ]
];
```

| Rule | Description |
| --- | --- |
| `minlength` | Minimum number of characters. Values below 8 have no effect: 8 is always the absolute minimum. |
| `maxlength` | Maximum number of characters. 1000 is always the absolute maximum. |
| `lowercase` | Require lowercase letters (or how many) |
| `uppercase` | Require uppercase letters (or how many) |
| `digits` | Require digits (or how many) |
| `symbols` | Require symbols (any character that is neither a letter nor a digit) |

### Regular expression or callback

For anything else, pass a regular expression or a callback as `rules`. Add a `hint` for the Panel and optionally a custom `error`. Both can be translated:

```php "/site/config/config.php"
<?php

return [
    'auth' => [
        'passwords' => [
            'rules' => '/^(?=.*\d).{16,}$/',
            'hint'  => [
                'en' => 'At least 16 characters, including a digit',
                'de' => 'Mindestens 16 Zeichen, davon eine Ziffer'
            ],
            'error' => [
                'en' => 'This password is too weak',
                'de' => 'Dieses Passwort ist zu schwach'
            ]
        ]
    ]
];
```

```php "/site/config/config.php"
<?php

return [
    'auth' => [
        'passwords' => [
            'rules' => function (string $password): bool {
                return str_contains(strtolower($password), 'kirby') === false;
            },
            'hint' => 'Please don’t use “kirby” in your password'
        ]
    ]
];
```

### Using the policy in your own code

You can reuse the same policy in your own forms, e.g. a frontend registration form:

```php
use Kirby\Exception\InvalidArgumentException;

try {
    $kirby->auth()->passwords()->validate($password);
} catch (InvalidArgumentException $e) {
    $error = $e->getMessage();
}

// describe the policy next to your password field
$hint = $kirby->auth()->passwords()->hint();
```

## Auth debugging

Any errors during authentication (e.g. invalid email address, wrong password or code, rate limit, errors during code generation or sending...) are by default hidden from the user. The user only gets the message "Invalid login" or "Invalid code". This prevents various attacks such as user enumeration (where an attacker would be able find out which users are registered on a site).

The real errors are logged to PHP's error log. They can be used to find the actual source of a login failure.

If you don't have access to the PHP error log, you can **temporarily** enable auth debugging to send the real errors to the user:

```php
<?php

return [
    'auth' => [
        'debug' => true
    ]
];
```

<alert>
Make sure to disable the `auth.debug` mode in production! Displaying auth errors on a public server can be a serious security risk because they could leak information to attackers.

In a production environment, please use the PHP error log to debug issues wherever possible.
</alert>
